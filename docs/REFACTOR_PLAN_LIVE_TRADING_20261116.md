# 量化交易系统全栈重构与正式实盘计划

版本：2026-11-16（Asia/Shanghai）

本文件是前端、后端、数据库、研究、币安 Demo 验收和正式实盘的统一实施计划。它是设计与实施依据，不代表当前代码已经实现这些能力，也不代表已经找到盈利策略。

## 1. 目标与边界

系统最终要支持完整链路：

市场数据 → 因子与订单流研究 → 成本回测 → 样本外与留出评估 → 策略冻结 → Binance Demo 验收 → 小额实盘校准 → 1000 USDT 实盘。

核心目标是尽可能保护本金，在可复核的真实成本后证据下寻找策略。允许长期空仓；没有合格策略时，结论必须是“未找到合格策略”，不能通过加杠杆、放宽风控、摊平亏损或凑交易数强行上线。

当前 Vue Vben、Python、PostgreSQL、既有 Demo 适配器和订单账本作为渐进迁移基础。前端页面全部重新设计；不把旧页面简单换色或搬到新目录。现有历史研究、冻结身份、成交和审计记录保留，迁移后仍可追溯。

## 2. 已冻结的产品协议

### 2.1 账户、市场与收益

| 项目 | 规则 |
| --- | --- |
| 市场 | Binance USDⓈ-M 永续；首批 BTC、ETH、TRX；允许多空 |
| 保证金 | 逐仓；最高杠杆 10x；关闭自动追加保证金；实际杠杆必须从交易所账户配置核验 |
| Demo 账户 | 独占一个 Binance Demo Futures 账户；正式开始前实测净资产为 1000 USDT、空仓、无普通或条件挂单 |
| 研究周期 | 1m、5m、15m、1h；盘口因子只在数据覆盖门槛通过后参与策略 |
| 交易日 | 北京时间自然日；数据库时间统一 UTC，并保存交易日边界 |
| 日净盈亏 | 当前账户净权益 - 日初净权益 - 当日外部净入金；包含浮盈亏、实际手续费、资金费和其它已确认现金流 |
| Demo 验收 | 连续 30 个北京时间自然日，累计净利润至少 1500 USDT，至少 100 笔完整往返交易，至少 18 个盈利日 |
| 稳定性分段 | 第 1–10、11–20、21–30 天三个固定分段，分段日末净利润均大于 0；不使用滚动 10 日窗口 |
| 复投 | 盈利保留但不扩大仓位；亏损后按较低净权益缩小仓位 |
| 失败裁定 | 日内净亏损硬超限、阶段最大回撤触线、未知事实无法补证等硬失败优先于样本不足 |

实际成交价已经包含真实滑点，计算真实净权益时不得再次扣除滑点。滑点单独作为执行归因指标；回测成本模型用预先冻结的保守滑点场景。

### 2.2 风险预算与冷却

1000 USDT 阶段的账户风险规则如下；100 和 300 USDT 阶段按 10% 和 30% 等比例缩放：

| 触发 | 1000 阶段 | 100 阶段 | 300 阶段 | 行为 |
| --- | ---: | ---: | ---: | --- |
| 三笔连续完整交易净亏 | 3 笔 | 3 笔 | 3 笔 | 撤销入口挂单，冷却 60 分钟 |
| 当日净亏冷却 | 20 | 2 | 6 | 暂停新增风险 2 小时 |
| 当日锁至次日 | 30 | 3 | 9 | 停止新开仓至次日 |
| 撤单并平仓锁日 | 40 | 4 | 12 | 撤销增加风险的订单，reduce-only 平仓，对账后仍锁定当天 |
| 硬失败边界 | 净亏严格超过 50 | 严格超过 5 | 严格超过 15 | 终止本轮，撤单、减仓、记录失败 |
| 阶段峰值回撤 | 150 | 15 | 45 | 终止本轮，保留历史，不自动恢复 |

风险状态优先级固定为：本轮失败 > 撤单平仓锁日 > 锁至次日 > 定时冷却 > 允许开仓。

规则细节：

- 单笔计划损失不超过风险基数 B=min(阶段起始本金, 当前净权益) 的 1%；所有持仓和入口挂单的计划风险合计不超过 2% × B；最多两个不同币种持仓；总保证金不超过 50% × B。这不是保证实际损失的上限。
- 连续亏损只由新完成的完整往返交易触发。部分成交不拆成多笔；盈利清零，零收益不清零；触发后消费这一组三笔事件。
- 日亏 20/30 的冷却只由新事件触发，不能因轮询或重复回报反复延长。并发触发取更高等级和更晚恢复时间。
- 日亏 40 触发后，必须持续撤入口单、reduce-only 退出并对账；确认空仓、无普通/条件挂单后仍保持当天锁定。
- 日内最低可验证净值用于日损判断；净值、标记价、资金费或订单事实缺失时停止新增风险并标记证据不完整。
- 跨日只重设日初基线，不清除尚未结束的冷却、锁定或阶段峰值。重启、刷新页面和切换策略不能解除状态。冷却结束后只接受新鲜信号，不补发旧信号。
- 任何已确认硬失败都优先于交易不足、费用缺失或无法评估。不能靠延长窗口、删除停机日或重置账户刷出通过。

### 2.3 开仓与退出

每笔开仓都必须生成不可变 EntryDecision，同时记录策略版本、输入数据指纹、信号时间、方向、价格、ATR、止损、目标、预计成本、计划风险回报比和所有拒绝原因。以下条件必须全部满足：

1. 冻结策略版本在当前环境获准，且产生了方向明确的新信号。
2. 指标已完成预热，所有输入在决策时已收盘可得；数据没有关键缺口、过期或时间错位。
3. 信号延迟、报价年龄和账户快照年龄在冻结策略的上限内。
4. 账户没有冷却、日锁、人工暂停、未知提交、对账冲突或保护故障。
5. 交易所实际逐仓模式、杠杆、精度、最小数量和最小名义额满足风险政策。
6. 入场、止损和目标在完整预计成本后计算，计划净收益/风险比至少 1.5。
7. 风险预算事务预占成功，且原生保护能力通过预检。

入口使用 post-only 限价单，默认等待 30 秒；不得自动追价转市价。未成交信号失效；部分成交立即进入保护流程。最小名义额无法满足风险预算时拒单，不能为凑交易提高仓位。

退出采用冻结策略版本中的退出参数：入场时冻结 R 和 ATR14，目标为 2R；达到 +1R 后将保护价上移/下移到覆盖实际入场费用、预计退出费用和保守滑点的位置，之后按冻结的 1 ATR 跟踪，止损只能向有利方向移动。初始止损倍数（例如 1 ATR 或 1.5 ATR）是研究参数，不在研究前预先当作最终规则。

原生条件止损/止盈、移动保护、账户风控退出和最大持仓时间都能触发退出；风险退出优先。目标持仓时间作为策略参数冻结，首版建议不超过 4 小时。所有退出只允许 reduce-only；平仓后清理剩余条件单，避免重复退出或反向开仓。

每次部分成交后必须确认保护数量覆盖实际持仓。新保护确认前不能撤销唯一有效的旧保护。保护拒绝、提交未知或超过工程确认时限时，立即撤销剩余入口、停止加仓并进入减仓与对账。2 秒是可监控的保护确认目标，不是绝对没有保护窗口的保证。

## 4. 后端、数据库和接口

### 4.1 后端模块

采用模块化单体，分为 identity/auth、market-data、research、portfolio/risk、execution、acceptance、operations。研究 worker 与唯一交易 writer 分进程运行；HTTP 请求不执行训练或长时间下单循环。

Demo 与实盘使用独立适配器、固定 host 白名单、独立凭据和独立账本。旧 Freqtrade 自动交易和代理写接口不能绕过新风险服务操作目标账户。一个账户只有一个可发交易命令的 writer；单机不引入自动主备抢占。

Mac 用 launchd 启动服务。睡眠、断网、数据库不可写、行情过期或账户对账失败时停止新开仓；交易所已确认的原生保护继续工作。重启后先检查账户模式、杠杆、余额、仓位、普通订单和条件订单，只恢复保护和对账；重新开仓需要人工恢复。接管前必须确认旧 writer 已停止。

### 4.2 数据库权威模型

PostgreSQL 是任务和交易状态的权威来源；大型行情、特征矩阵和模型继续存外盘，数据库登记 URI、SHA-256、时间范围和质量结论。金额、数量和费率使用 NUMERIC/Decimal；时间使用 UTC。

新增或规范化以下模型：

- 研究：dataset_versions、factor_versions、strategy_versions、experiment_runs、run_metrics、run_artifacts。
- 交易：accounts、capital_stages、order_intents、orders、conditional_orders、fills、cashflow_events、equity_marks。
- 风控：risk_policies、risk_days、risk_reservations、cooldown_states、追加式 risk_events。
- 验收：acceptance_runs、acceptance_days、acceptance_decisions、approval_events。

引入显式、可回滚的 SQL 版本迁移。服务启动只检查兼容版本，不在普通连接初始化时执行整份 schema。旧文件和 JSONL 作为可追溯导入/导出兼容层，不再作为任务状态的唯一真相。迁移前做备份，迁移后在隔离库恢复并校验订单、成交、资金、研究事件和冻结身份。

### 4.3 版本化 API

新增按领域拆分的版本化 API：accounts、risk、factors、strategies、runs、execution、acceptance、data、operations。保留旧 iterations 和历史查询路由，直到新旧读数完成对照。

所有风险和验收响应至少包含：environment、account_id、strategy_version_id、run_id、as_of、data_quality、cost_completeness、status、reason。金额和数量以十进制字符串返回。交易命令包含稳定幂等键，未知提交必须查询确认，不能自动重发形成第二单。

## 5. 因子、订单量与价格研究

### 5.1 研究内容

研究三层数据：

1. 成交订单流：成交数量、USDT 成交额、成交笔数、单笔规模、主动买卖比例和累计成交差。
2. 可见盘口：1/5/20 档失衡、价差、深度斜率、盘口变薄和报价持续性。
3. 价格变化：收益、速度、加速度、波动、突破、回撤、量价背离、延续与反转。

订单量突增、盘口失衡或统计相关不自动构成方向性开仓信号。先分别检验它们预测方向、预测波动、改善成交和改善风险的能力。当前 20 档聚合快照不能声称知道全市场真实挂单数、撤单量或队列位置；断档和序列不连续时该段盘口特征无效。

### 5.2 实验协议

- 每个币种/周期/数据源先通过覆盖率、缺口、延迟、时间对齐和标签成熟检查。缺少足够盘口历史时，只从采集开始做前向研究，结论为 not_estimable。
- 首批至少使用 365 天可信 K 线；最后 90 天只作一次最终留出。此前采用训练 120 天、验证 30 天、步长 30 天滚动评估，并按标签跨度做 purge/embargo。
- BTC、ETH、TRX 首轮采用单币时间序列和组合级评估，不把需要至少 5 个币的横截面 IC 判据套在 3 个币上。
- 成交额突增先用前 288 根已完成 5m K 线的滚动中位数，当前根不进入基线；2x、4x、8x、20x 作为预注册分档。研究未来 1/5/15/30/60 分钟方向、波动、最大有利/不利偏移和误报率。
- 完整实验族最多 120 个配置，计入币种、周期、因子组合、退出参数和成本场景的笛卡尔展开。实验清单、随机种子、成本模型和比较方法在运行前冻结；所有尝试和失败均留档。
- 使用时间块 bootstrap/HAC 处理重叠样本，并对完整实验族做多重比较校正。验证集只用于筛选，最终留出失败后不能反复调参重测。
- 订单流策略必须报告成交率、部分成交率、未成交机会成本、延迟和逆向选择；实际 Demo 净收益不得重复扣滑点。

压力场景固定为：手续费翻倍、不利滑点翻倍、资金费支出翻倍，资金费收入按原值保留。只有预注册的基准和压力场景都通过，候选才有 Demo 准入资格。

### 5.3 策略入选

“最优”定义为候选集合中同时满足风险、数据、执行和成本门槛，且成本后样本外收益下界与稳定性最高的版本；合格集合可以为空。

进入 Demo 前至少满足：完整交易不少于 100 笔；成本后净收益为正；利润因子至少 1.2；日损和峰值回撤合规；执行和成本压力场景不出现负收益；所有策略、规则、代码、数据、成本和风险 hash 一致。回报不稳定、成交率不足、资金费缺失或保护无法验证时保持不可评估。

## 6. Binance Demo 与正式实盘生命周期

### 6.1 Demo 30 天

一个验收轮次只能运行一个冻结策略，或一个事先冻结组成、权重和风险预算的组合。切换策略必须空仓、无挂单、完成对账并人工批准，同时创建新验收轮次。

正式开始前核对独占账户净资产 1000、逐仓模式、实际杠杆、允许交易对、手续费率、用户数据流和原生条件订单。Demo 不支持某项硬保护时，阻止正式验收，不偷偷降级为收盘轮询。

30 天窗口从固定北京时间时刻开始，首尾均空仓、无未决普通/条件订单；停机日保留。最后一天停止新开仓并完成退出与对账。硬失败、证据不足和完整通过按固定优先级裁定。

### 6.2 小额实盘校准

Demo 全部严格条件通过后，人工批准 100 USDT、300 USDT、1000 USDT 三个实盘阶段。100 和 300 是执行校准，不是稳定盈利证明。每阶段从固定启动时刻累计，至少观察 7 个自然日和 20 笔完整往返交易；累计净收益需为正、费用/资金对账完整、无硬风险违规、保护和未知订单记录合格。未满足交易数继续观察，不能挑选最好的一周；出现硬风险违规则该阶段失败。

资金升级必须空仓、无普通/条件挂单、所有成交和费用对账完成；转入资金单独记为现金流，不能算收益；新阶段建立新的日初和阶段净值基线，旧阶段不覆盖。1000 阶段必须重新完成完整 30 天验收。

每次新策略上线、策略切换、资金升级和异常恢复都需要人工批准；批准后系统才允许自动交易。研究 worker 不能自动替换当前实盘策略。

### P0：协议、基线和设计系统

- 冻结本文件中的风险、成本、账户、环境和验收协议。
- 盘点当前未提交改动、旧 API、历史账本、Demo 会话和运行服务；不覆盖用户数据。
- 完成新前端信息架构、设计 token、状态字典和 API 草案。

验收：所有旧功能有新入口或明确退役记录；策略、环境、账户和资金阶段身份没有歧义。

### P1：Demo 安全纵向切片

- 先实现账户权益/资金费、风险日状态、冷却、风险预占、订单幂等、普通/条件保护、成交对账和恢复。
- 接通新交易台与验收页最小版本，不等待全站 UI 完工。
- 用离线 stub 和隔离数据库验证 Demo 与实盘 host/凭据隔离；不发送真实订单作为开发测试。

验收：跨日、浮亏、资金费、重复回报、部分成交、未知提交、保护失败、重启和数据库故障场景均符合状态机。

### P2：研究与数据门槛

- 建立数据版本、因子版本、订单流/盘口事件成熟和实验族注册表。
- 实施每频率覆盖检查、成本模型、成交模型、滚动验证、留出集和可复核产物。
- 只有通过研究门槛的冻结版本进入 Demo 预检。

验收：未来数据扰动不改变历史信号；缺口不被填零；重复实验不冒充新证据；策略产物可离线复现。

### P3：全新前端页面

- 依次交付交易台、验收与上线、因子/订单流、策略、实验任务、数据、运维证据、设置和系统页。
- 每页同时实现正常、空、未知、过期、失败、部分成交、冷却和硬失败状态。
- 新旧读数对照和浏览器流程通过后，再移除旧页面入口；历史链接进入准确的历史定位页。

### P4：Demo 30 天与实盘校准

- 只运行一个冻结身份，保存每日权益、成本、冷却、订单、成交和证据快照。
- 通过后由人工审批 100 USDT，完成固定校准；再分别审批 300 和 1000。
- 任何阶段失败都保留完整证据，不自动重置或延长窗口刷通过。

## 8. 测试与发布关口

### 后端、数据库与执行

- 风险：并发预占、三笔连亏、日亏 20/30/40/超过 50、峰值回撤、跨日、浮亏、资金费、入金、冷却重启和状态优先级。
- 订单：post-only 未成交、部分成交、最小名义额、未知提交、重复幂等、条件单保护、新旧保护替换、止盈/止损竞态、残留订单清理。
- 对账：REST 与用户流重复、手续费补记、资金费补记、现金流、余额、仓位、普通订单和条件订单一致性。
- 研究：标签不泄漏、数据缺口、成熟窗口、缓存身份、实验族上限、成本方向、成交率和留出集一次性评估。
- 恢复：数据库备份恢复、Mac 进程重启、断网/睡眠恢复、旧 writer 停止确认和紧急日志合并。

### 前端

- Vitest、类型检查、生产构建和关键浏览器流程进入 CI。
- 覆盖研究到冻结、冻结到 Demo 预检、成交到完整成本对账、冷却触发与恢复、日亏锁定到验收失败、人工批准资金升级。
- 在 1920、1440、768、390 宽度检查风险栏、表格、抽屉、图表、键盘焦点、对比度和错误状态。

### 发布与回滚

- 发布前验证待交付 commit 的 CI 成功、数据库迁移版本、配置 hash、策略/成本/风险身份和备份恢复结果。
- 代码回滚不得恢复旧数据库副本、删除新成交、清除风险锁或降低已生效策略保护。
- 实盘发布仍需人工批准；没有批准不发送真实下单请求。

## 9. 不可变限制与成功定义

- 1000 USDT、日均 50 USDT、日损和回撤阈值是验收协议，不是收益保证。
- 日均 50 USDT 相当于不复投本金的日收益率约 5%，与保本优先存在显著张力；如果没有候选在成本和风险约束下通过，系统必须停止上线并继续研究。
- Binance Demo 是模拟环境，真实执行、盘口和费用可能与正式环境不同；Demo 通过也不等于正式实盘必然盈利。
- 本地 Mac 的睡眠、断网、系统重启和磁盘故障可能造成超限风险；原生交易所保护是上线硬条件，但不能保证绝对不亏。
- 研究结果、Demo 结果和实盘结果必须分环境、分账户、分策略版本统计，不得混合宣称收益。

最终交付物为：全新前端、模块化后端、显式数据库迁移、研究/订单流/成本协议、风险与冷却状态机、Demo/实盘适配器、测试与 CI、运行手册、恢复演练记录，以及每个阶段可独立复核的证据包。
