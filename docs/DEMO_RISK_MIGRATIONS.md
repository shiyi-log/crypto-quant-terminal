# Demo 风险账本迁移与恢复

本小节对应 2026-11-16 重构计划的显式数据库迁移关口。迁移由
`DemoStore.ensure_schema()` 明确执行；`DemoStore.check_schema()` 只核对版本和
SHA-256，不自动补跑迁移。缺少迁移包、未知版本、历史版本空洞、校验和漂移
或待升级状态均拒绝新增风险。

## 安装与检查

先对目标 PostgreSQL 做一致性备份，并在隔离库恢复验证；确认旧交易 writer 已
停止后再执行显式安装。不要把开发用的 `quant_test` 测试命令指向运行账户库。

1. `0001_demo_risk_events` 创建风险事实表；金额保存在事件 payload 的十进制字符串中。
2. `0002_risk_event_integrity` 增加持久化追加序号，并用 ALWAYS 触发器阻止
   UPDATE、DELETE、TRUNCATE。相同事件 ID 的完全相同重试幂等，不同事实会回滚
   整个批次；同一账户的事务锁串行化追加。
3. 每次运行读取按 `sequence_id` 重放，不能按交易所时间或事件 ID 重排。

升级前已有记录没有可靠的追加序号。第二版迁移只能按已有
`created_at/timestamp_ms/event_id` 固定旧顺序；不能将这个顺序当成已经证明的
历史到达顺序。升级后的新记录具有确切序号。

## 代码回滚

风险证据不能通过恢复旧数据库副本回滚。新版数据库遇到不认识迁移版本的旧
代码必须停止新增风险；继续保护、对账或安装兼容修复。已写入的新成交、
冷却、风险锁和终止事实全部保留。任何修正必须追加新事实，不直接改历史。

## 验证与当前限制

2026-11-16 在随机 schema 的 PostgreSQL `quant_test` 执行
`./.venv/bin/python -m pytest tests/test_demo_store.py -q`：45 项通过、20 个子测试
通过。覆盖同毫秒/迟到事件顺序、冲突批次原子回滚、并发重试、真实只读事务
兼容检查和直接 SQL 改删截断拒绝；检查结束删除该测试 schema。

全局 `DataStore.initialize()` 仍执行历史 schema 安装流程，因此本小节只证明
Demo 迁移检查路径只读，尚未满足整个仓库“普通连接不隐式执行 schema”的目标。
生产备份恢复演练及全局连接生命周期迁移仍待执行。
