# 发现：实测延迟吃掉秒级边际的 43~81% —— 且与 3 秒 TTL 冲突

> 2026-10-12 · DSH · 目标第 75 轮 · 直接输入用户的「秒级/高频」测试

## 一、实测延迟（来自真实 Demo 成交，非估计）

由 `demo_orders` 毫秒字段算得（session `manual_smoke_20261012_035400`）：

| | 第 1 笔 | 第 2 笔 |
|---|---:|---:|
| signal → submission | **2961 ms** | 2 ms |
| submission → exchange_updated | **2298 ms** | 2250 ms |
| **端到端** | **5259 ms** | **2252 ms** |

## 二、延迟对秒级毛边际的侵蚀（用 209 万实盘快照合成）

方法：信号在 `i` 产生，成交推迟 `L` 毫秒，出场仍在 `i + H`。
样本：BTC 10Hz 快照 2,098,995 个。

| 持仓 H | 延迟 L | 无延迟毛边际 | **有延迟毛边际** | **衰减** |
|---:|---:|---:|---:|---:|
| 10s | 0 ms | 0.538 bp | 0.538 bp | 0% |
| 10s | 2250 ms | 0.541 bp | **0.250 bp** | **53.7%** |
| 10s | 5259 ms | 0.541 bp | **0.105 bp** | **80.6%** |
| 30s | 2250 ms | 0.636 bp | 0.346 bp | 45.6% |
| 30s | 5259 ms | 0.637 bp | 0.201 bp | 68.5% |
| 60s | 2250 ms | 0.669 bp | 0.379 bp | 43.4% |
| 60s | 5259 ms | 0.669 bp | 0.233 bp | 65.1% |

**⇒ 秒级的真实毛边际是 0.105 ~ 0.379 bp，
而成本是 4.02 bp（maker）/ 8.02 bp（taker）
⇒ 只有成本的 【1.3% ~ 9.4%】。**

## 三、物理解释

OBI（订单流失衡）预测的是**当下**的短期价格压力。
推迟 2.25~5.26 秒执行时，失衡已经反转/消散 —— 所以 43~81% 的预测力消失。

**这与微观结构文献一致**：订单流失衡的预测力集中在**亚秒到数秒**，
衰减极快。而我们无法在亚秒级执行（实测端到端 2.25 秒起）。

## 四、⚠️ 与秒级链 3 秒 TTL 的设计冲突

Codex 的实现（`demo_second_level_runner.py`）：

```
line  78: maker_ttl_seconds: int = 3
line 113: "maker_ttl_clock": "3_seconds_from_local_submission_claim_request_start"
line 416: ttl = submission_mono[client] + maker_ttl_seconds
line 426: if mono() >= ttl and not cancellation_attempted: 撤单
```

**⚠️ TTL 从【本地提交】起算 3 秒，而实测延迟 2.25~5.26 秒：**

| 场景 | 后果 |
|---|---|
| 延迟 5.26 s（首次连接） | 订单到交易所时 TTL 已过期 → **每单都被撤** |
| 延迟 2.25 s（已建连接） | 订单在交易所只挂 **0.75 秒** → 成交率极低 |

**⚠️ 这是「秒级」定义与「可执行性」的本质冲突：**
- 要「秒级」，TTL 必须短（否则挂单 30 秒就不是秒级）
- 但实测延迟 ≥2.25 秒，短 TTL 会让订单几乎无法成交

**⚠️ 值得肯定的是**：Codex 把时钟语义**显式写成 `maker_ttl_clock` 字段**，
使这个冲突**可见**而不是隐藏 —— 这是正确做法。

## 五、建议（供 Codex 与用户判断）

| 选项 | 内容 | 代价 |
|---|---|---|
| **A** | 保持 TTL=3s，接受低成交率 | 成交样本少 → 样本积累慢 |
| **B** | TTL 拉到 8~10s（覆盖实测延迟） | 「秒级」语义被削弱，但仍远短于 runner 的 30s |
| **C** | 同时跑两组 TTL（3s 与 10s）作为独立 arm | 需要扩展 arm_schedule |
| **D** | 记录每笔的 `latency_ms` 与 `ttl_remaining_ms`，让裁定能事后分层 | 不改行为，只加证据 |

**我的倾向**：**D + C** —— 先用 D 把证据记全（不改行为），
再考虑把 TTL 作为第 9/10 个 arm（因为 TTL 本身就是一个待研究的自变量）。
