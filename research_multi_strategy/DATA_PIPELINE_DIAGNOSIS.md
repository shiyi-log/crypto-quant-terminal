# 数据流诊断报告：实验室为什么"跑不出结论"

> 建立：2026-10-12 · DSH
> 结论：**实验室看到的有效历史只有设计值的 ~15%（120/750 根），根因是数据层，不是策略层。**
> 在修复之前，任何策略实验都无法得出统计结论。

---

## 1. 一句话结论

实验室的原生周期策略（15m/1h）需要 750 根热身数据，**实际只拿到 113 根(15m) / 27 根(1h)**。
根因是一条四环链条，每一环都独立存在、且都未被修复。

## 3. 逐环证据

### 环 1 · market_stream 只覆盖 BTC/ETH 的 5m

```
database/runtime/market_stream_status.json:
  pairs: ["BTC/USDT:USDT", "ETH/USDT:USDT"]
  market: futures · transport: websocket

→ TRX 无实时流 → TRX 策略无法参与前向
→ 15m/1h 无实时流 → 依赖导入
```

### 环 2 · closed 标记稀疏（7~28%）

```
近 30 天 BTC、带 extras.closed=true 的行数 vs 期望:
  5m  602/8,640 =  7.0%     15m 199/2,880 =  6.9%
  1h  199/720   = 27.6%     1d   29/30    = 96.7%

对照（不看标记，只看数据在不在）:
  5m 95.6% · 15m 95.6% · 1h 98.2% · 1d 100%
→ 数据是齐的，缺的是标记
```

**修复点（单行）**：`data_sync.py:403`

```python
# 现状
"extras": clean_payload({col: value for col, value in row.items() if col not in columns})
# 修复
extras = clean_payload({col: value for col, value in row.items() if col not in columns})
extras["closed"] = True        # 历史 K 线按定义已收盘
```

> ⚠️ `data_sync.py:369/389` 是 `upsert_series` 的 funding_rate/oi 路径，**不是 K 线**，不需要改。

### 环 3 · 缺口（这才是绑定约束）

```
_history 只保留最后一个缺口之后的连续段:

  5m : 2 处缺口
       2026-10-09 07:40 UTC → 2026-10-10 10:25 UTC  缺 321 根（26.8 小时）
       2026-10-08 07:20 UTC → 2026-10-08 11:45 UTC  缺  53 根
       → 缺口后连续仅 363 根
```

## 5. 为什么这件事比"再设计几个策略"重要

```
已确认：
  · 实验室 29 个账户运行数小时，仅 7 笔开仓、2 笔平仓
  · 21 个账户 decision = 0（其中 10 个因 warmup 永久阻塞）
  · warmup 只有设计值的 15%

推论：
  即使某个策略真有边际，在 warmup 不足 / 数据陈旧 / 只覆盖 BTC/ETH 的条件下，
  它也【无法在合理时间内积累到可裁定的样本量】。
  所以修复数据供给的收益，远大于再加 10 个策略。
```

## B. 🔴 我的 3 处实质错误

### B1. 缺口计数 off-by-one（精确错误）

若报告中的左右时间是**已存在的两根 K 线**，缺失数应为 `delta/step − 1`：

| 缺口 | 我写的 | 正确 |
|---|---|---|
| 5m 10-09 07:40 → 10-10 10:25 | 321 根 | **320 根** |
| 5m 10-08 07:20 → 11:45 | 53 根 | **52 根** |
| 15m 10-08 07:15 → 10-09 01:15 | 72 根 | **71 根** |

**→ 321/53/72 是「间隔数」，不是「缺失数」。**

### B2. 🔴 我说「本地无源数据，回补必须重新下载」——过度概括

**复核找到的本地源**：`bot/user_data/data/orderflow/BTC_5m_orderflow.feather`

```
288,001 行完整 OHLCV · 2024-01-12 15:40 → 2026-10-08 15:40 · 0 内部缺口
288,001 行【全部通过 closed_candles 校验】
覆盖原小 5m 缺口（52 根）；重采样还可覆盖 15m 缺口 33 根
与标准 futures 最近 2000 根重叠 OHLCV【各字段差异为 0】
来源：bot/fetch_orderflow.py:71 → Binance 合约 fapi/v1/klines
```

**⚠️ 正确表述**：标准 feather 的终点确实等于缺口起点（这部分我对），
**但「标准文件没有」≠「本地所有源都没有」**。
大 5m 缺口与剩余 15m 缺口超出已核验 feather 范围，那部分才需重新下载。

**→ 教训：报「无源」前，必须先穷举本地所有可能的数据源（含 orderflow/衍生目录）。**

### B3. 「5m 缺口是绑定约束」——算术复现，但因果未被证明

```
✅ 复现: 截 BTC 10-10 10:25 → 10-11 16:35 的 363 根 5m
        → 真实 resample_closed_candles 生成 120 根 15m / 29 根 1h（算术正确）
⚠️ 但: 窄区间算术【不能证明】load_spec_candles 实际只能取到 120/29，
      更不能独立证明旧 valid_bars=113/27
```

**当前状态（复核时）**：`load_spec_candles(limit=750)` 对 BTC/ETH 两周期**均返回 750 根**；
当前代码把**直接表与重采样结果按 timestamp 合并**，不会简单丢弃旧直接历史。

**⚠️ 一个易错判读（复核提醒）**：用墙钟 18:09 会 `ready=False`，
但原因是 **`closed_candle_stale`**，`valid_bars` 仍为 750 ——
**不能把 stale 误判为「热身根数不足」。**
